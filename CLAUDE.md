# go-parties-admin · working rules for Claude Code

The admin command center and the API (Express + Prisma + Vite/React, one process, Railway). The customer storefront is a separate repo, `go-parties-app`; its `CLAUDE.md` and `docs/` (GO-PRODUCT, GO-ROADMAP, GO-LOG, BRAND) are the shared source of truth. Read them first. Docs-only commits to that repo's `docs/` are fine when architecture changes; never edit storefront code from here.

## Navigation rule (permanent)

The admin is built from one config, `src/nav.tsx`. The sidebar, the routes, the breadcrumb and the redirects all come from it, so adding a page is one line there.

- A section with one screen is a direct sidebar link (`path` + `element`).
- A section with two or more screens is an expandable sidebar group (`pages`). Each sub-page is its own address and gets a full page.
- No in-page tabs anywhere in admin. A long stacked page is split into sub-pages. (Filters on one list, like a status filter, are not navigation; they are buttons with `aria-pressed` or a select, never `role="tab"`.)
- Every screen has its own URL. Filters that a link needs to carry (from an Overview card, say) go in the query string, and are read by a small route component in `nav.tsx`.
- The group containing the current route opens itself on load. Each group's open or closed state is remembered per group (localStorage).
- Collapsed to icons, a group's icon opens a small flyout of its sub-pages. On narrow screens the sidebar is a drawer opened from the top bar.
- The breadcrumb at the top of each page is the nav path ("Settings / Business rules").
- Every old address, including old tab query strings, redirects to its new home. When a page moves, add the old address to `LEGACY_REDIRECTS` (or `LEGACY_TABS` for a group's old `?tab=`). Never leave a bookmark or an already-sent link broken.
- `src/nav.test.tsx` enforces this (groups have two or more pages, addresses are unique, every redirect lands on a real page). Run `npm test`.

Room is left, not built, for: Leads groups, Settings > Account and access. (Messages > Upcoming exists, first in the Messages group.)

## How work is done here

- Node: `source ~/.nvm/nvm.sh && nvm use 20` before any npm or npx. Build gate, always with pipefail: `set -o pipefail && npx tsc -b && npx oxlint . && npm run build`.
- Production is the only database (Railway Postgres). Test rows are prefixed "ZZ ", cleaned up afterward, and the cleanup is confirmed with a count.
- Migrations: Railway applies them before every deploy (`railway.json` runs `npx prisma migrate deploy --config prisma7.config.ts` as the pre-deploy command, inside Railway, against the private database URL). Nobody runs migrations from a laptop any more. Write the migration, test it on a throwaway database (`zz_scratch_*`, drop it afterward), show the SQL summary and stop for confirmation, then push: the deploy applies it. Never `migrate dev` against production. Make schema changes additive first (add columns, then drop later) so the running build keeps working, and so a failed pre-deploy step leaves nothing broken.
- Writing rules for chat, code comments, commits and docs: no em dashes, no hype, plain direct sentences. Brand voice for customer-facing copy is in the storefront's `docs/BRAND.md` section 10.
- Every automated text and email goes through `sendTemplatedMessage` (`server/sendTemplated.ts`) and a trigger in `server/triggers.ts`. Do not call the Twilio or email wrappers directly for an automated message.
- Anything timed goes through the planner (`server/automation/planner.ts`). The sender, the record timelines, the Leads chips and Messages > Upcoming all read its output; never add a second place that decides what is due. New timed messages are a milestone in the planner, a trigger in the registry, and a test in `server/tests/planner.test.ts`.
- Server tests need DATABASE_URL in the environment: `npx tsx --env-file=.env --test server/tests/*.test.ts` (or `set -a; source .env; set +a` before `npm test`). They use the production database with stubbed Twilio and clean up their own rows.
- Anything that decides who holds a gig goes through `acceptOffer` / `submitBid` in `server/bids.ts`, which take a row lock on the gig. Never update gig or offer status for a bid outside those functions. The public crew page response is built only in `serializeBid`; add a field there only if it is safe for a crew member who has not been picked.
- Public routes cost money or can be abused, so each has a gate. Anything new that calls the Anthropic API goes through `aiGate` (`server/ai.ts`), which keeps one shared daily budget (staff sessions are counted, never limited). Anything new that writes from the public storefront gets `botCheck`, a small body limit in `server/index.ts`, a per-IP limiter, and `safeInline` on every free-text field a customer types (names and notes end up in texts we send).
- Nothing sensitive in the server log: use `redact`, `maskPhone`, `maskEmail` and `safeErr` from `server/log.ts`, never `console.*(err)`, a message body, a token or a phone number.
- CORS: a route the storefront calls must be added to `PUBLIC_ROUTES` in `server/security.ts`; every other route is the admin's and gets no CORS. The CSP is in the same file; if a page needs a new external host, change it there and test the page in the browser pane.
- What goes into an AI prompt is public data only (never `Item.notes`). Customer-facing JSON is built field by field, never by spreading a database row.
- Tests that touch the production database stopped being acceptable after the security block (2026-10-05). New tests must be pure or run against a throwaway database.
- Contract sending has one set of rules, in `server/contractSend.ts` (pure, tested) and carried out by `sendContract` in `server/notify.ts`. Only a real send marks a contract Sent, starts the 48-hour reminder and moves a Held booking to Contract Sent. `prepareContract` only makes the link; previews and anything else that is not a send must use it and never mark anything. Do not add another place that sets `contractStatus`, `contractSentAt` or the Contract Sent stage.
- "Deposit" is an identifier only (`depositPercentage`, `{{depositAmount}}`, `deposit_percentage`, the JSON keys). Everything a person reads says "retainer". Never rename the identifiers, and never edit a saved policy version: staff save a new one.
- The login lockout (`attemptLogin` in `server/loginLimit.ts`) records the attempt first and reads the count second, so a burst cannot slip past it. Keep any new rate or count check atomic the same way (take first, give back on failure), never "read the count, then write it".
- The GO contract (format go-v2) is built in `server/contract/`: `goTemplate.ts` is the client's wording verbatim with the business numbers as tokens (never retype a number into it), `goDocument.ts` composes the locked document the storefront renders (field by field, nothing internal), `goPdf.ts` draws the replica, `goLoad.ts` is the only database reader. `server/tests/goContract.test.ts` proves the template matches `server/tests/fixtures/go-contract-blank.reading-order.txt` character for character; if the wording must change, change the template and the fixture together with the client's sign-off, never one of them. The response shape in `server/routes/contracts.ts` is locked with the storefront's `contract/types.ts`; do not add or rename fields without changing both.
- Google Calendar (`server/google/`) is one way: the app writes to Google and never reads changes back. Every booking change calls `queueGoogleSync(bookingId)` after the response is sent (never awaited in a booking flow), and `syncBooking` never throws: a failure is stored redacted on the booking and retried by the hourly `reconcileCalendar`. The customer invite is built only in `inviteEventPayload`, field by field; nothing internal (crew, other phones, notes, admin links) goes in, and `server/tests/google.test.ts` asserts it. GO's event never has attendees. Tokens: the refresh token is stored only encrypted (`encryptToken`), access tokens are minted per sync and never stored, and no token or Google URL with a token is ever logged. Tests mock Google with `setGoogleFetch`; no test makes a real Google call.
- Staff accounts (Block U, `server/users.ts`, `server/routes/auth.ts`, `server/routes/team.ts`): every admin request runs inside `runAsActor` (set by `requireAuth`), so a record that should say who did it reads `currentActor()` or spreads `actorFields()`; never add a `userId` parameter to a function for this. Owner-only routes are gated with `requireOwner` on the server (the UI's read-only note is a courtesy, not the control); the Owner list is Settings > Team, Business rules, Policies and contracts, Contract terms, Contract settings and Integrations, and the settings PATCH splits by field (`STAFF_FIELDS`). There must always be one active Owner with a password (`changeRole`, `removeUser`); removing a person deactivates the row so their name stays on the logs. Invite and reset links are stored only as a SHA-256 hash, work once (`consumeToken` is an atomic update) and expire after 72 hours. TOTP secrets are sealed with a key derived from COOKIE_SECRET (`server/secrets.ts`); rotating that secret turns everyone's two-step off. A login answer never says whether an email exists. Tests: `server/tests/team.test.ts` refuses to run unless DATABASE_URL names a `zz_scratch` database.
- Tiers, payments and delivery (Block T1, `server/tiers.ts`, `quotes.ts`, `payments.ts`, `stripe/client.ts`, `delivery.ts`, `portal.ts`): the tier is decided only by `decideTier` (review rules first, then the contract rules, else the rental policy) and the storefront never names one that is trusted; `POST /api/bookings/direct` recomputes it and refuses a mismatch with `tier-changed`. A tier 2 quote (`issueQuote`) is the GO contract composed from the cart with GO's signature pinned to midnight Eastern of the quote day; the hold rebuilds it (`checkQuote`) and refuses `quote-expired` or `contract-changed` on any difference, then signs through `signContractFromQuote` (the one other place, besides `signContract`, that writes a ContractDocument and sets `contractStatus` Signed; it exists because the customer signed at checkout). Every amount is computed in `amountsFor` from the booking, the signed document and the recorded payments; a browser never names an amount. Stripe is called over fetch with one pinned API version (`STRIPE_API_VERSION`, default `2025-09-30.clover`); tests replace it with `setStripeFetch` and never call Stripe. Only a verified webhook event (`applyStripeEvent`, idempotent by event id) or `paymentStatus` retrieving a complete and paid session from Stripe marks a payment succeeded; `applyPaid` is the only place that flips `retainerPaid` and `balancePaid` from money. The webhook route reads a raw body (mounted before the JSON parser) and a bad signature writes nothing. Delivery is stored as sent and checked afterwards by `verifyBookingAddress` (Places API New, `setMapsFetch` in tests); the check never blocks or changes a booking. The portal's customer-facing shape is built field by field in `server/portal.ts` and locked with the storefront's `customerApi.ts`; tier 2 and 3 bookings refuse self-serve cancel, reschedule and change-item with "Call or text GO to change this booking." Tests: `server/tests/tiers.test.ts` (pure) and `server/tests/checkout.test.ts` (refuses to run unless DATABASE_URL names a `zz_scratch` database).
- Accounts and the home address (Block A5): "Require an account to book" (`requireCustomerAccount`, Business rules, off by default) is enforced only at the top of the public hold in `server/routes/directBookings.ts` (401, reason `account-required`); staff bookings through `staffBookingRouter` never check it, and nothing else creates a booking from the storefront. A customer's `homeAddress` is one line of text set at sign-up, by `PATCH /api/customer/me` (name, phone, home address; never the email) or by a signed-in hold when the account has none (never overwritten by a hold). The booking's `address` stays the event address that delivery, crew and the calendar read; `eventAddressSameAsHome` is a record only. The balance due day count is the one `balanceDueDays` (Contract settings) that the contract text binds and `GET /api/settings/public` publishes. Tests: `server/tests/accounts.test.ts` (throwaway database only).
- Home page photos (Block A6, `server/hero.ts`, `server/routes/hero.ts`, `server/heroSeed.ts`): the slides live in the database as WebP (`processHeroImage` is the one place that resizes to 2000px, converts and makes the 400px thumbnail; the routes and the seed both call it). A slide's bytes never change under its id (no replace route: a new photo is a new slide), which is why `GET /api/media/hero/:id` is cached for a year and marked immutable; keep it that way. `GET /api/hero` is the public list, active slides only, built field by field; both public routes are in `PUBLIC_ROUTES` behind `availabilityLimiter`. Uploads are one file per request as raw bytes (`express.raw` on the admin POST only, 15 MB cap in `hero.ts`), never a data URL in JSON. The prebuilt sharp on Railway reads JPEG, PNG and WebP; HEIC (HEVC) is accepted by type but refused with a plain sentence when it cannot be decoded. Tests: `server/tests/hero.test.ts` (throwaway database only).
- Item description (Block A7): `Item.description` is the one customer-facing line (240 characters, `MAX_DESCRIPTION_LENGTH` in `server/routes/items.ts`, cleaned with `safeInline`); `notes` stay internal and never leave the server. Every public item shape carries `description` through `toPublicItem` (catalog and Ask GO) and the packages feed; the Ask GO prompt line (`catalogLine`) may include it because it is public by definition, and still never `notes`. Tests: `server/tests/itemDescription.test.ts` (throwaway database only).
- Staff notifications (Block A10, `server/notifications.ts`, `server/routes/notifications.ts`): the bell and the morning digest. Every notification has a `dedupeKey` and goes in through `createNotifications` (insert, skip duplicates), which is what makes a condition fire once; new producers follow that. New leads fire inline through `notifyNewLead`, which never throws (website, concierge and storefront holds; Ask GO leads and staff-made leads do not notify), and every tier 3 request through `notifyDesignRequest`, whose link is the Open list because no booking exists until staff convert it. Timed ones are worked out in `findDueNotifications` (reads only) and written by `runTimedNotifications`, called from `runAutomation` on real runs only. The digest is a planner milestone (`planDigest`), the trigger `staff_daily_digest`, and one idempotent send a day from the first pass at or after 7 AM Eastern; its contents are the fixed window `digestWindow` (7 AM yesterday to 7 AM today), so a late pass cannot change them. The three wedding checks are stubs answering false until the questionnaire exists; replace their bodies, not the producers. `/notifications` is in NAV with `hiddenFromSidebar` because the bell is the way in. Tests: `server/tests/notifications.test.ts` (throwaway database only) and the digest cases in `server/tests/planner.test.ts`.
- Hidden items and per-guest packages (Block A8, `server/packagePricing.ts`): `Item.hidden` keeps an item in the admin and on existing bookings but out of every public response (the catalog, the packages feed's item lines, Ask GO) and refused by `resolveCart` and the public hold with reason `hidden`; staff bookings ignore it. A package is priced in one place, `packagePrice` (fixed: the bundle; per_guest: basePrice + price x guestCount inside minGuests to maxGuests), which the tier call and the hold both go through; `guestCount` is part of `QuoteCart`, printed on the quote as expectedGuests so the hash changes with it, and stored on the booking. Tests: `server/tests/hiddenPerGuest.test.ts` (throwaway database only).
- Wedding details (Block A11, `server/weddingDetails/`): `template.ts` is the client's form as data, wording the client's except that its em dashes became commas, colons and periods (house style), every field a stable key; never rename or reuse a key, a wording change is a new template version. `logic.ts` is pure: `isWeddingBooking` (staff `weddingOverride` wins; else the booking's own occasion decides when it has one; the package's occasions count only when it has none), `prefillFor` (computed live, never stored; a key with a value is locked and refused on save, a key with nothing stays editable), `cleanAnswers`, `sectionProgress` (only stored answers count, so prefill alone never finishes a section). `store.ts` is the only writer and saves under a row lock. Answers never go in a message; if one ever does, it needs `safeInline`, because fields marked `keepLinks` keep links. The form is behind the customer session and answers 404 for anything but their own wedding booking. Customer reminders are planner milestones, email only, and start OFF (`emailDefaultOn` unset) because the link goes to a storefront page: turn them on in Messages > Templates once that page exists. Tests: `server/tests/weddingDetails.test.ts` (throwaway database only) and the reminder cases in `server/tests/planner.test.ts`.
